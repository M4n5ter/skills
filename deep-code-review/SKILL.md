# Deep Code Review

产出高信号、可用于工程决策的代码审查。

默认只读。只有用户明确要求修改实现时才编辑代码。

审查完成的标准是：

- 每项实质性变更及其直接影响对象均已纳入判断
- 每项 finding 均经过主 reviewer 独立验证
- correctness 与 design 分别得到明确结论
- 已验证的问题、未验证的风险和普通建议得到清楚区分

## 1. 理解审查对象

确定：

- 审查对象及其比较基准
- 变更或实现的目标
- 受支持的调用方、输入和运行环境
- 明确约定的行为、约束和 breaking changes

阅读必要的实现、调用方、依赖、测试、配置和文档。上下文范围由实际依赖决定，不由文件列表机械决定。

只报告由审查对象引入、恶化或实际暴露的问题。与当前范围无关的既有问题不进入 findings。

明确意图内的行为变化不是回归；实际影响超出声明范围时再报告。

## 2. 建立 Risk Map

不要预设所有项目具有相同风险。

对每项实质性变化判断它涉及哪些维度：

- 可观察行为和结果
- 输入、数据与控制流
- 接口、调用方和依赖
- 状态、资源与副作用
- 失败、取消和恢复行为
- 信任边界与敏感数据
- 性能、交互和运行环境
- 测试提供的行为保障

只深入调查实际存在的维度。

Risk Map 完成的标准是：每项实质性变化都有对应的行为影响判断，并且所有直接受影响的受支持调用方或契约都已 accounted for。

## 3. 选择审查模式

根据用户请求选择一种模式：

- `correctness`：聚焦行为错误、安全问题、回归和测试可靠性
- `design`：聚焦职责、边界、复杂度、抽象和可维护性
- `full`：同时使用两个视角；全面深度审查默认使用此模式

普通审查由主 reviewer 完成。

只有用户明确要求并行 reviewer 时才启动两个只读 reviewer：

- 一个使用 correctness 视角
- 一个使用 design 视角

向两者提供相同的原始审查对象、比较基准和必要上下文，只指定各自视角，保留独立发现能力。

主 reviewer 逐项验证、去重和裁决返回结果。多个 reviewer 得出相同结论会提高复核优先级，但不代替证据。

当前环境无法并行时，依次执行两个视角。

## 4. Correctness 视角

根据 Risk Map 检查：

- 实现是否满足已确认的行为和契约
- 受支持输入、边界输入和相关失败路径是否产生正确结果
- 数据、状态、资源和副作用是否保持一致
- 错误、取消、重试或恢复是否破坏已经确定的结果
- 被修改的接口、数据格式、配置或运行环境是否保持所需兼容性
- 涉及信任边界时，权限、验证和敏感数据处理是否正确
- 性能变化是否会对受支持场景产生实质影响
- 测试是否经过需要保护的真实路径，并会在行为破坏时失败

测试存在不代表行为已经得到验证；测试缺失本身也不自动构成 finding。

## 5. Design 视角

判断实现是否是完整解决当前问题的最小清晰表达：

- 职责和所有权是否明确
- 模块边界是否降低耦合和读者工作集
- 新增状态、分支、模式和间接层是否由真实需求支付
- 类型和数据模型是否直接表达约束
- abstraction 是否净减少概念、重复或控制流复杂度
- shared code 是否承担了不属于它的策略
- 相同事实或行为是否存在多个实现来源
- API 和依赖面的扩张是否必要
- 实现是否利用了已有且合适的代码库约定
- 测试是否验证可观察行为，而不是锁定内部形状或编排细节

文件长度只作为职责混杂的线索，不单独构成问题。

拆分、提取或新增 abstraction 只有在降低整体理解成本时才是改进。

一项 design finding 只有同时满足以下条件时才阻塞：

- 当前实现造成了实质性设计退化
- 退化会带来真实维护成本或错误风险
- 存在范围受控的替代方案
- 替代方案能够净删除概念、状态、分支、重复或依赖

## 6. 验证 Findings

一项确定 finding 必须能够通过受支持的调用方式、输入或契约触发。

对每项候选问题确认：

1. 触发条件
2. 实际执行或状态路径
3. 可观察影响
4. 与当前审查对象的因果关系
5. 最小修复方向

严重度遵循当前代码库的既有约定。没有既有约定时使用：

- `blocking`：会导致重要行为错误、安全问题、数据风险或不可接受的设计退化
- `important`：真实且值得在当前范围内修复，但不阻止整体方向成立
- `non-blocking`：不会否定当前实现，但会影响后续工程判断

严重度由影响和可达性共同决定，不按理论最坏情况判断。

涉及安全、权限或数据完整性的边界，可以根据该边界必须防守的输入评估，不要求先出现事故。

继续调查尚未闭合的候选问题。最终无法验证时，将其标记为 residual risk，或从结果中删除。

优先提出消除根因的最小修复。能够删除状态、分支或重复事实的方案优于继续追加补丁。

省略样式 nit、纯个人偏好和不能提高决策信心的建议。

## 7. 检查外部审查信息

存在 PR、MR 或其他 review discussion 时，先完成独立审查，再读取已有评论和自动审查结果。

逐项验证外部 finding。有效内容纳入统一结论并注明来源；外部结论使用与自身 finding 相同的证据标准。

## 8. 输出

按严重度降序、findings first 输出。

每项 finding 包含：

- 严重度与简洁标题
- 精确位置
- 触发条件
- 可观察影响
- 关键证据
- 最小修复方向

没有确定 finding 时明确说明，不使用低价值意见填充结果。

最后分别给出：

- `Correctness`：acceptable 或 not acceptable
- `Design`：acceptable 或 not acceptable
- `Validation`：已执行、失败和未执行的验证
- `Residual risk`：当前条件下仍无法确认的事项

输出格式适配用户请求和当前协作平台。

评论、approve、request changes 或其他外部写操作仅在用户明确授权后执行。

## 9. 修复后的复核

用户要求修复时，由主 agent 实现，并执行与风险相称的验证。

修复后优先重验原始触发条件、受影响契约和相关回归路径。

只有用户明确要求，或修复实质改变了行为、设计或 Risk Map 时，才重新运行完整深度审查。

同一边界持续产生同类 finding 时，重新检查问题模型；优先选择能够删除状态和特殊情况的结构性修正。
