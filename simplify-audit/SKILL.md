# Simplify Audit

## 目标

最大化净简洁度：减少维护者必须同时理解和保持一致的概念，而不是追求删除行数或列出更多候选。

优先寻找可以完整消失的：

- 重复 authority 或镜像状态
- 只转发、不收敛职责的抽象
- 没有生产需求的兼容路径和扩展点
- 同一契约的多种 representation
- 已失去行为价值的测试与 fixture

默认只读。用户明确要求实施后，才修改代码。

## 审计模式

### Bounded（默认）

围绕一个 PR、模块、domain 或明确问题审计。检查直接生产调用方、状态 owner、持久格式和关键测试即可。

不要求全仓 coverage table，也不要求穷举每个文件或每种 slice。

对于 PR，先继承或建立同一份 Review Charter：一句话目的、支持路径、非目标和 Merge bar。审计对象是该 PR 引入、依赖或明显恶化的复杂度。与目的无关的既有复杂度默认留在范围外；只有 PR 无法在不处理它的情况下正确交付时，才进入“现在做”的候选。

### Repository-wide

仅在用户明确要求全仓架构简化时使用。此时可以建立 concept map 和分阶段删除计划，但仍按收益排序，不做形式化清点本身。

## 建立当前模型

先用一句话说明范围的职责，再回答：

- 哪些事实必须存在？
- 谁是每项事实的唯一 owner？
- 哪些边界是公共 API、协议、持久格式或外部集成？
- 当前有哪些真实使用方和兼容要求？

只有理解现有行为后，才能判断某层是冗余还是必要隔离。

存在并行或多轮审计时，共享 Review Charter 和轻量 Finding Ledger。已 rejected、follow-up 或 accepted 的候选，只有在新证据、相关代码变化或目标模型变化时才重新打开。独立重读用于校验证据，不用于重置范围。

## 候选信号

重点搜索：

- 两处保存或推导同一事实
- constructor、adapter 或 wrapper 只做 rename / forward
- 生命周期由多个 owner 重复 close、retry、recover 或 reconcile
- 类型允许无意义或非法的 optional 组合
- composition root 同时知道过多 domain 细节
- 为假想使用方保留的 mode、flag、fallback 或兼容 decoder
- 只断言调用次数、内部顺序、常量镜像或 wrapper 存在的测试
- 多个小修复围绕同一个缺失的边界或错误 owner 堆条件

这些只是线索，不自动成为结论。

## 简化候选准入门槛

一项建议只有同时满足以下条件，才进入最终报告：

1. 会删除或合并一个独立 mental model、authority、state、path、contract 或 representation
2. 不会把等量复杂度搬到别处
3. 保留当前需要的行为，或明确指出要有意识移除的行为
4. 迁移与验证成本和收益相称
5. 对维护、可靠性或理解成本有可说明的实际收益
6. 对 PR 审计而言，它减少的是当前变更引入、依赖或恶化的 mental model

若只是代码更短、命名更顺眼、多一层“更抽象”，不算简化。

实施前检查 Scope Delta。需要新增 owner、状态、协议、公共契约、依赖或跨子系统职责的方案，通常不是当前 PR 的净简化；只有这些新增内容是交付 Charter 目的的最小必要条件时才继续。以概念和边界计算净收益，不使用行数作为预算。

## 证据标准

证据强度按边界调整：

- 公共 API、协议、持久数据、rolling recovery 和第三方集成：需要明确消费者、迁移或兼容证据
- 仓库内部私有实现：限定范围搜索、生产调用链和现有需求通常足够；不需要证明所有假想未来都不可能出现
- 安全与数据边界：不能为了简洁删除仍在承担真实保护作用的机制

历史上曾修过 bug，不足以永久保留一层抽象或一个测试；应判断当前结构是否已从根因消除了该风险。

## 净收益判断

对候选比较简化前后：

- 需要理解的概念数
- authority 和状态 owner 数
- 分支、生命周期和错误路径数
- representation / conversion 数
- 测试与迁移负担
- 对真实行为和故障边界的影响

净收益既按单项也按拟采用的候选组合计算。若多个候选分别简化局部、组合后却增加整体 owner、状态、契约、边界或重复机制，则组合方案是负收益；只保留能共同收敛到最小目标模型的候选。

删除 100 行但新增一个隐式约定，可能是负收益。增加少量直接代码但删除一个同步状态机，可能是正收益。

## 测试也是审计对象

保留能验证稳定行为、关键不变量和高价值故障边界的测试。

优先删除或合并：

- 只复述实现细节的 mock / call-count / call-order 测试
- 同一行为被多个窄 regression 重复覆盖
- 被删除兼容路径的专属 fixture
- 重构后由类型或更高层测试自然覆盖的单元测试

不要因为某问题曾被 reviewer 提出，就自动永久新增测试。测试的长期价值应独立成立。

## 输出

默认只输出三类结果：

1. **值得现在做的简化**：说明可删除的概念、证据、目标模型和净收益
2. **需要产品或兼容决策的门槛**：明确缺少哪项真实决策，不把它伪装成代码问题
3. **没有值得做的简化**：这是有效结论

按收益排序，而不是按文件顺序。每项建议应回答：

- 删除什么，而不仅是新增什么
- 为什么当前需求不再需要它
- 哪些行为必须保持
- 最小验证方式是什么

不默认输出覆盖表、长清单或所有观察。低收益 polish 直接省略。

## 与 Deep Code Review 联用

Simplify Audit 不是第二轮 correctness review。Deep Code Review 负责风险、缺陷和 Merge bar；本审计只比较其当前或拟议方案的 mental model 净变化。两者共享 Charter 和 Finding Ledger，结果统一裁决一次，而不是拼接两份待办列表。

## 删除验证

只有一次有界检查能决定一项高收益删除是否安全时，才建议 deletion probe。默认不提供 probe；确有需要时最多三个，并写明：

- 要证明或证伪的假设
- 最小实验或查询
- 通过后能删除什么

不要为了获得“完整信心”设计大型临时 harness。

## 停止条件

当高收益候选已经闭合、真实决策门槛已经暴露，且继续搜索只会产生局部 polish 时停止。

后续小修不自动触发新的全量 simplify audit；只有引入新的 owner、状态机、协议、持久 representation 或兼容层时，才重新审计相关范围。
