# 类型系统纪律（Type System Discipline）

**适用场景：** 在设计类型、审查函数签名或使用任何静态类型语言编写代码时使用。让非法状态无法表示，为具有语义的基础类型加上品牌标记，在边界处解析外部数据，拒绝向编译器撒谎，穷尽变体，并从权威模式定义派生类型。

让编译器拒绝不可能的状态、错配的基础类型值和未处理的变体。与其不断增加处理器，不如优先通过定义让错误和特殊情况根本无法出现。有关 TypeScript 的具体建模方式和代码示例，参阅 [TypeScript 类型建模](typescript-type-patterns.md)。

- **让非法状态无法表示。** 将变体建模为和类型（可辨识联合、带载荷的枚举、密封类），而不是一堆允许矛盾组合通过编译的可选字段。`{ completed: boolean; completedAt?: Date }` 允许 `completed: true` 却没有日期。从 `completedAt` 派生布尔值，或者建模为 `{ kind: 'open' } | { kind: 'done'; at: Date }`。如果你能写一条注释来说明字段组合在什么情况下有效，就将它拆成和类型。
- **类型是构造，不是限制。** 从你想要的值出发构建类型，而不是从更宽松的类型中靠检查筛出这些值。非空列表就是一个头元素加上其余元素。有效的时间区间就是一个起点加上一段时长。选择无法构造出非法值的形态，再在其上提供调用方所需的接口。
- **为具有语义的基础类型加上品牌标记。** `UserId` 和 `OrderId` 底层都是字符串，但不应该能相互替换。为两者各自定义类型，例如 TypeScript 中带品牌标记的交叉类型，或其他语言中的 newtype。在创建时校验一次，下游信任类型。如果两个参数使用相同的基础类型却含义不同，就为它们加上品牌标记。
- **外部数据在解析前都是无类型的。** RPC 载荷、JSON、IPC 消息、CLI 参数、配置文件、环境变量、数据库行都是如此。在每个边界设置解析函数，将非结构化输入转换为有类型的模型。[边界纪律（boundary-discipline）](boundary-discipline.md)原则技能说明了校验应该放在哪里。
- **不要向类型系统撒谎。** 绕过编译器的类型强制转换、不安全转换和断言函数，都是潜在的运行时崩溃。如果编译器无法证明某个事实，就去证明它（校验、收窄、细化模型），或者承认这个强制转换是一项隐患。将每个 `any`、`as` 或 `assertNotNull` 追溯到边界，并在那里校验。
- **穷尽匹配是编译器的工作。** 对和类型的匹配，必须在新增变体却没有处理它时编译失败，这样编译器就能告诉下一个智能体应在哪里补上分支。使用所用语言的惯用方式：TypeScript 中类型为 `never` 的绑定，Rust 中不加注解的 `match`，Haskell 中的 `-Wincomplete-patterns`，Kotlin 中密封类匹配的穷尽性检查。
- **从权威模式定义派生类型。** 如果某种数据形态由 protocol buffer、OpenAPI 规范、GraphQL 模式定义、数据库迁移、设计令牌文件或其他文件定义，就从该来源派生类型，而不是手写一套平行类型。参阅[把经验固化到结构中（encode-lessons-in-structure）](encode-lessons-in-structure.md)原则技能。
- **只在非全定义性出现的地方强化类型。** 运行时断言、空值检查或“这不应该发生”的抛错，都标记着类型过于薄弱的地方。将这项检查上推到类型中，然后就到此为止。类型系统的职责是跟踪每个使用点必须处理的情况，而不是尽可能精确地描述数据。优先使用全函数。空列表的 `sum` 是 0，所以它接受普通列表。空列表的 `head` 没有答案，所以它要求非空列表。如果不这样强化也不会有任何地方发生 panic，就保留普通类型。
