# 为领域建模（Model the Domain）

**适用场景：** 在编写有状态逻辑时，或代码分支很多、对数据结构形态的同一假设在多个文件中反复出现时使用。

将真实领域编码进数据结构，而不是把它分散在条件判断中。与领域匹配的结构能让无效状态无法表示，并消除分支。在编写时选对结构，成本很低；事后找回这种结构，会被视为一次重构，进而被推迟。

优先考虑：

- 用状态机代替分散的布尔值、阶段或生命周期检查。
- 用有类型的模型代替松散的参数或反复出现的数据形态假设。
- 用映射、注册表、查找表或可辨识联合代替散落在多个文件中的分支。
- 用归约器（reducer）或命令／事件模型代替临时拼凑的状态修改。
- 围绕同一组领域知识组织模块，而不是按加载、校验、转换、保存这样的顺序组织。执行顺序不等于归属。
- 用一个小型模块边界归拢重复的行为、归属关系或不变量。
- 在访问模式需要时，使用队列、缓存、索引、图、树或规范化集合。
- 其他任何合适的结构。如果没有现成结构合适，就先弄清代码绝不能允许什么，以及数据会如何被读取，再找到恰好编码这些要求的结构。

不要强行抽象。如果当前形式已经清晰、局部化，而且不太可能继续增长，就优先选择朴素的代码。对于只增加间接层，却没有消除分支、重复规则、无效状态或生命周期风险的抽象，要持怀疑态度。

你跳过了这一步的迹象是：一个新功能让现有的 if/else 链又多了一个分支，或者出现了一个必须与第一个布尔值保持同步的第二个布尔值。按时间顺序拆分也是一种迹象。以阶段命名的模块会在不同步骤中重复同样的领域规则。
