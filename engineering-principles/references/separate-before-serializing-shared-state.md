# 先隔离，再串行化共享状态（Separate Before Serializing Shared State）

**适用场景：** 在并发执行方可能写入同一个文件、分支、键或状态对象时使用。先消除共享；只有在必须由一个写入方写入共享状态确实是不变量时，才从结构上强制串行化。

当并发执行方可能共享可变状态时，先问它们是否需要同一个可变对象。如果不需要，就消除共享。如果共享确有必要，就从结构上强制串行化：锁文件、顺序执行的阶段、独占所有权。指令和约定不是并发控制。

**为什么：** 对共享状态的并发写入会产生竞态条件，这类问题间歇性出现、难以复现，调试成本高昂。

**模式：**
1. **识别共享可变状态**（双方都读写的文件、双方都推送的分支、双方都定义并使用的 API）。
2. **默认做法：消除共享的写入目标。** 问一问：这些执行方需要一个唯一的权威对象，还是在发布彼此独立的事实？让每个执行方拥有自己的文件、键、分支或状态目录，只在读取／报告边界进行合并。两个工作进程将各自的 `lastX` 字段写入同一个 `state.json`，仍然是在修改共享状态；分别使用 `indexer-state.json` 和 `metrics-state.json` 则不是。
3. **只有在必须写入同一个共享目标确实是不变量时，才从结构上串行化访问**（锁文件、顺序执行的阶段、单写入方 actor，或原子的比较并交换）。将“我们需要一把锁”视为一种需要检查的设计异味，而不是默认答案。
