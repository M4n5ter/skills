# 修复根因（Fix Root Causes）

**适用场景：** 调试时使用。将每个症状追溯到根因，并在根因处修复；先复现，不断追问为什么，直到找到根因，抵制通过添加 nil 检查来掩盖崩溃的做法。

调试时，不要只修复症状。将每个问题追溯到根因，并在那里修复。

**原因：** 针对症状的修补会不断累积。每个变通方案都会让系统更难理解，而真正的缺陷依然存在。修复根因前期较慢，却能减少总调试时间。

**做法：**
- 先复现。
- 不断追问“为什么”，直到找到根因。
- 不要添加防护判断（添加 nil 检查来消除崩溃，就是在修补症状）。
- 如果需要一整段注释来为某个变通方案辩护，那就是代码有问题（修复代码，而不是注释）。
- 检查整个问题模式，而不只是眼前这一处（用 grep 搜索相同模式，修复所有实例）。
- 卡住时，添加观测手段，不要猜测（添加日志、读取实际错误）。
- 如果决定性事实需要深挖才能找到，就提出一种低成本、始终开启的信号，让它下次能在第一眼就显现出来。

**重启相关的缺陷：先怀疑状态，再怀疑代码**

当某个功能“重启后失效”时，首先怀疑陈旧的持久化状态：配置文件、缓存、锁文件、序列化状态。如果清除某个状态文件就能恢复行为，应优先通过状态校验来修复。
