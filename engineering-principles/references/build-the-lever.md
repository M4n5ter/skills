# 构建杠杆工具（Build the Lever）

适用场景：任何非琐碎工作，而不只是批量工作，包括编辑、迁移、分析和检查。构建完成或证明这项工作的工具（codemod、脚本、生成器，或让子代理遵循的技能），不要手工做。工具就是审阅者可以重新运行的产物。

当工作并不琐碎时，构建完成它的工具，而不是手工完成。

codemod、生成器或脚本每次都以相同方式工作，可以零额外手工劳动地重跑。工具是一个审阅者可以阅读并重新运行以检查工作的产物。手工改动只能通过重新做一遍来复核。确定性脚本把“相信我”变成“运行这个”。

默认构建杠杆工具。只有任务确实琐碎，例如一眼就能看明白的两三处修改，才跳过。

- 先手工做第一个单元，学会操作方法，再构建工具。把工具在该单元上重新运行，将结果与手工版本做差异比较来证明它正确。让工具能够安全重跑。
- 编辑用 codemod 或脚本，重复文件用生成器，分析用导出到 SQLite 后查询，验证用可重跑的检查。
- 确定性工具胜过分派并行任务。如果工具能一次处理所有单元，就自己运行它。不要把脚本能做的事分派给代理手工做。
- 向子代理分派任务时，把杠杆写成所有子代理都会阅读的技能：将操作方法、验证契约和禁止改动的范围放在同一份产物中。将它放在被委派者的可写范围之外，避免它们悄悄改写契约。
- 应用这条原则会产出一个文件。如果引用了它，但差异中没有 codemod、脚本、生成器或委派技能，就没有真正应用它。
- 如果工作会延续到当前会话之后，就提交这个工具。

门槛是工作是否琐碎，而不是是否重复。即使只做一次，只要工具让工作变得可检查，它也值得构建。按照[懒惰协议](laziness-protocol.md)，构建能完成或证明任务的最小脚本，绝不构建框架。

它不同于[把经验固化到结构中](encode-lessons-in-structure.md)，后者把重复出现的指令变成持久护栏。本原则关注眼前工作的吞吐量和可审阅性。关于把验证本身脚本化，参见[证明它确实可用](prove-it-works.md)。
