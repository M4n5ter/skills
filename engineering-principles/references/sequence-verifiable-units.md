# 把工作组织为可验证单元（Sequence Work into Verifiable Units）

**适用场景：** 多步骤工作（批量修改、迁移、一连串相似的编辑），以及安排提交和 PR 的堆叠顺序时使用。将工作拆成小单元，每个单元都以可验证的状态结束；检查完当前单元再开始下一个，并安排好交付顺序，让审查者能从这个顺序本身看出工作成立的证据。

将工作安排成一连串小单元，每个单元都以可以检查的状态结束；当前单元的检查通过之前，不要继续往下做。

**原因：** 在引入故障的那个单元就发现故障，定位成本很低。等一批工作做完才发现，故障就会被埋在其中，而且你已经在损坏的基础上继续构建。将这些单元组织成审查者能够重放的交付序列，就能把“相信我”变成“看它先失败，再通过”。

**执行。** 在批量修改、迁移或任何一连串相似的编辑中，开始下一项之前，先验证当前变更。每个单元都由前后状态框定：已知正确的状态、一次变更、运行检查，然后继续。先变基到干净的主干上，确保每次检查都以真实基线为参照。当编辑由杠杆工具完成时，逐单元检查的成本几乎为零。即便如此，也要运行检查。

**交付。** 按照能够证明工作正确的顺序堆叠提交和 PR。典型形式是先提交失败的测试，再在其上提交修复。其他叙事顺序包括：先删减再重塑、先捕获基线再实施改动、先搭脚手架再实现功能。每个提交都能独立落地，整个序列读起来就是一段论证。

这条原则从顺序安排上补充了[证明它确实可用（prove-it-works）](prove-it-works.md)原则技能，后者确保每次检查都针对真实对象；也补充了[构建杠杆工具（build-the-lever）](build-the-lever.md)原则技能，后者让逐单元检查变得便宜。
